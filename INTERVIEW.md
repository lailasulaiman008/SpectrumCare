## 1. Decision Log — Why I Chose X Over Y

### Decision 1: TypeScript over plain JavaScript for the backend

I chose TypeScript for the Node.js backend because it catches an entire class of bugs at
write-time that JavaScript would only surface at runtime. When you are writing a Prisma query
that joins User, Child, Screening, and GameSession, having the compiler tell you that
`child.screenings[0].answers` is a string (not a parsed object) prevents a runtime crash in
production. The tradeoff is a build step and a steeper learning curve, but for a backend that
handles auth and medical screening data, type safety is worth it.

The alternative was plain JavaScript. I would have gotten faster iteration initially but more
brittle code as the project grew.

### Decision 2: SQLite over PostgreSQL

I chose SQLite because it requires zero infrastructure. There is no separate database server
to spin up, no connection string to a remote host, no managed database service to pay for.
The entire database is a single file (`prisma/dev.db`) that lives alongside the code. For a
project being deployed on Render's free tier where the goal was to keep everything zero-cost
and simple to demonstrate, SQLite was the right call.

The tradeoffs I accepted: SQLite does not support concurrent writes well (it uses file-level
locking), JSON columns are stored as serialized strings (requiring explicit `JSON.parse()` on
read), and the database is ephemeral on Render's free tier — it resets every time the service
restarts because there is no persistent disk. For a demo or portfolio project, these are
acceptable. For a production medical app with real users, I would switch to PostgreSQL with a
managed provider like Supabase or Neon.

### Decision 3: Prisma over raw SQL or other ORMs (Sequelize, TypeORM)

I chose Prisma because it has the best TypeScript integration of the available Node.js ORMs.
The Prisma client is auto-generated from the schema, meaning every query is fully typed — the
return type of `prisma.user.findUnique(...)` reflects the exact shape of the data, including
which relations were included. This makes refactoring safer.

Sequelize and TypeORM are older and more established, but their TypeScript support is bolted on
rather than native. Raw SQL would have given more control but less safety and more boilerplate.

### Decision 4: JWT over session-based authentication

I chose JWTs because they are stateless — the server does not need to look anything up in a
database or session store to verify a request. The token is self-contained and signed. This
fits the architecture well: the frontend stores the token in `localStorage`, attaches it to
every request, and the `authMiddleware` just calls `jwt.verify()` to confirm it is valid and
extract the user ID.

The alternative would be server-side sessions (storing session data in a database table or in
Redis and giving the browser a session cookie). Sessions are arguably more secure for some
threat models because they can be invalidated server-side instantly. JWTs cannot be revoked
before they expire (this project uses 7-day expiry). For a production app, I would either use
short-lived JWTs with refresh tokens, or move to sessions. For this project's scope, the
simplicity of stateless JWTs was the right call.

### Decision 5: Logistic Regression over a neural network or gradient boosting

I chose Logistic Regression for the ML model because the problem is simple and the model needs
to be explainable. The M-CHAT-R is a 20-question binary questionnaire with well-defined clinical
scoring rules. A logistic regression model that learns those rules is interpretable: you can
look at the coefficients and understand which features the model weighted most heavily. It also
trains in milliseconds on the synthetic dataset and is trivially serializable with joblib.

A neural network would have been overkill — the dataset is 2000 synthetic samples generated
from the clinical rules themselves. A complex model would just overfit to rules I already
coded explicitly. Gradient boosting (XGBoost, LightGBM) would perform similarly to logistic
regression on this data with no meaningful benefit. The SHAP library also has a
`LinearExplainer` specifically optimized for linear models, making explanation straightforward.

### Decision 6: Synthetic training data over real clinical data

I generated synthetic data for the model because I do not have access to real patient data,
and obtaining it would require IRB approval, data sharing agreements, and patient consent
frameworks that are outside the scope of a portfolio project.

The synthetic data is generated by `train_model.py` using the same scoring rules that are
implemented in `mchat-scorer.ts`. This means the model is essentially learning to replicate a
deterministic algorithm with noise added. I am honest about this: the model is not a real
clinical predictor. It serves as a demonstration of an XAI pipeline — showing how you would
integrate SHAP explanations into a health application if you had real data.

### Decision 7: Separate Python microservice for AI instead of a JavaScript ML library

I chose Python/Flask for the AI service because Python's machine learning ecosystem
(scikit-learn, SHAP, numpy) is far more mature and well-documented than JavaScript equivalents
like TensorFlow.js or ONNX.js. SHAP, in particular, does not have a full-featured JavaScript
port. The tradeoff is added deployment complexity — two separate services on Render instead of
one — and a network call between them on every screening submission (with a 5-second timeout
to handle cases where the AI service is unavailable).

The microservice approach also means the AI component is independently deployable and
testable.

### Decision 8: Flask over FastAPI for the Python service

I chose Flask over FastAPI because this service has two endpoints, no async operations, and
no need for OpenAPI schema generation. Flask is simpler for a small service. FastAPI would be
the better choice if I were building a larger API with complex request/response validation,
because FastAPI uses Pydantic for automatic validation and generates interactive documentation.
For two endpoints, Flask's simplicity wins.

### Decision 9: Render over Vercel, Netlify, Railway, or Fly.io

I chose Render because it can host both a Node.js backend and a Python service together on a
single free account using a Blueprint configuration file (`render.yaml`). Vercel and Netlify
are primarily designed for static sites and serverless functions — hosting a persistent Express
server with a file-based SQLite database would be awkward or impossible on those platforms.
Railway and Fly.io are strong alternatives and would support this architecture, but Render's
Blueprint feature (which provisions multiple services from one YAML file) made it the clearest
fit for demonstrating infrastructure-as-code.

### Decision 10: Single HTML file frontend over React or Vue

I chose a vanilla JavaScript single-page application in one `index.html` file rather than a
React, Vue, or Next.js frontend. The reason is that the project already has two services
(Node backend, Python AI), and adding a framework build pipeline for the frontend would add
a third build step, a third port in development, and a more complex deployment. For a project
that can be fully described by one index.html served by the Express backend, this avoids
unnecessary complexity.

The tradeoff is that the code in the `<script>` block gets harder to maintain at scale. With
3502 lines in the file, there is already some readability pressure. For a larger application
with many more pages and components, I would move to React or Next.js.

## 2. Bug Archive — Debugging Stories

These are bugs and tricky problems I can identify from examining the actual code, patterns, and
comments.

### Bug 1: AI service URL with missing `http://` prefix

**Symptoms:** The screening endpoint would throw a networking error even when the AI service was
running, with a message like `Only absolute URLs are supported` or similar fetch errors.

**Root cause:** On Render's private networking, the `AI_SERVICE_URL` environment variable is
provided in `host:port` format (e.g., `spectrumcare-ai:5001`) without the `http://` prefix.
The Node.js `fetch()` function requires a fully qualified URL.

**Fix:** In `screening.ts` (lines 38-40), an explicit check was added:
```typescript
if (!aiServiceUrl.startsWith('http://') && !aiServiceUrl.startsWith('https://')) {
  aiServiceUrl = `http://${aiServiceUrl}`;
}
```
This guard prepends the protocol only when missing.

**What I learned:** When building services that communicate via private networking, do not
assume the environment variable will always include the protocol. Normalize it defensively.

### Bug 2: Non-Latin1 characters crashing PDF generation

**Symptoms:** The PDF download would either fail entirely or produce a corrupted PDF when a
child's name or any text contained emoji or non-standard characters.

**Root cause:** The `pdf-lib` library encodes text using standard fonts (Helvetica), which only
support Latin-1 characters (code points 0-255). Emoji, curly quotes, and many Unicode
characters are outside this range and cause encoding errors.

**Fix:** The `safe()` helper function in `pdf-generator.ts` (line 24):
```typescript
const safe = (s: string) => s.replace(/[^\x00-\xFF]/g, '?');
```
It strips any character outside the Latin-1 range before passing text to `pdf-lib`.

**What I learned:** Never pass user-controlled strings directly to libraries that have
character encoding constraints. Sanitize at the boundary. The cleaner long-term fix would be
to embed a custom font that supports the full Unicode range.

### Bug 3: Prisma client instantiated once per route file (N instances)

**Symptoms:** Potential too-many-connections warnings or subtle connection pool issues under
load. Each route file (`auth.ts`, `child.ts`, `screening.ts`, etc.) calls
`const prisma = new PrismaClient()` at module level, creating separate client instances.

**Root cause:** Looking at the code, every route file independently creates its own
`PrismaClient`. With five route files, that is five separate instances. Prisma recommends
using a single shared instance across the application.

**Current status:** This is a code architecture issue that exists in the current codebase. For
SQLite on a single-service deployment, it works in practice because the connection overhead
is minimal. For PostgreSQL with a connection pool, this pattern would exhaust the pool.

**The fix** would be to create a single `prisma.ts` file that exports one shared `PrismaClient`
instance, and import that singleton in all route files.

**What I learned:** Prisma's documentation recommends the singleton pattern explicitly. It is
easy to miss when initially building route files independently.

### Bug 4: Game session saving fails silently when user is not logged in

**Symptoms:** A user who somehow navigates to the games page without completing auth can play
games but the session is never saved. No error is shown.

**Root cause:** In `endGame()` in `index.html` (around line 3399), the session save is gated
with `if (state.childId && state.token)`. If either is null, it silently skips the API call.

**Current handling:**
```javascript
if (state.childId && state.token) {
    try {
        await apiCall('/api/game/session', { ... });
    } catch (e) { console.error('Failed to save game session:', e); }
}
```
The catch logs to console but does not show the user any message.

**What I learned:** Silent failures in user-facing features are a UX problem even when they
are "correct" from an error-handling standpoint. The user might play multiple sessions thinking
they are being tracked. A better approach would be to show a brief toast notification: "Sign in
to save your progress."

### Bug 5: Login form creates a new child if user has no children

**Symptoms:** A user who logs in without a child profile (for example, a user whose data was
deleted due to Render's ephemeral storage, but whose account still exists) unexpectedly gets a
new child profile created automatically with a generic name.

**Root cause:** In `handleLoginAndScreen()` (line 3147), if `data.children.length === 0`, the
code immediately creates a child with `{ name: "your child", ageMonths: ageYears * 12 }`.
This means the child gets a default name and the age entered on the login form.

**What I learned:** Login forms should not have side effects like creating records. The flow
would be cleaner if login simply authenticated the user and then redirected to a "set up your
child profile" step if no child exists.

## 3. Q&A Drill — 40 Interview Questions

### Project Overview

**Q1: What is SpectrumCare? Describe it in 30 seconds.**

SpectrumCare is a full-stack web application that helps parents screen toddlers for autism risk
using the M-CHAT-R questionnaire, a clinically validated tool. Parents answer 20 yes/no
questions, the app applies the clinical scoring algorithm and optionally an AI model, and
returns a risk classification with explainability through SHAP values. There are also three
simple cognitive games the child can play, with session tracking and a progress dashboard.
Parents can download a PDF report to bring to a pediatrician.

**Q2: Who is the intended user of this app?**

Parents of toddlers aged 16-30 months who want a preliminary screening tool before or between
pediatrician visits. The app explicitly disclaims that it is not a clinical diagnosis and
recommends consulting a healthcare professional. It is not designed for clinicians.

**Q3: What does the M-CHAT-R stand for and why did you use it?**

Modified Checklist for Autism in Toddlers, Revised. It is a publicly available, validated
screening tool recommended by the American Academy of Pediatrics for children 16-30 months.
I used it because it provides a concrete, defensible framework for the scoring logic. The
20-question structure, the at-risk answer mapping (some questions where "yes" is at risk, others
where "no" is at risk), and the LOW/MEDIUM/HIGH thresholds (0-2, 3-7, 8-20) are all from the
published clinical documentation.

**Q4: What are the three main features of the app?**

First, M-CHAT-R screening: 20-question flow with real-time progress bar, resulting in a risk
classification and an explanation of which answers contributed most. Second, therapy games:
three cognitive games (emotion face matching, odd one out, color tap) with accuracy and
response time tracking. Third, progress reporting: a weekly dashboard and a downloadable PDF
report combining screening results and game performance.

### Architecture

**Q5: Describe the overall system architecture.**

There are three components. A single HTML/CSS/JavaScript frontend that is a single-page
application served by the Node.js backend. A Node.js Express backend written in TypeScript
that handles all API routes, authentication, database operations via Prisma, and PDF
generation. A Python Flask microservice that hosts the ML model and returns predictions with
SHAP explanations. The backend calls the AI service via HTTP on every screening submission,
with a 5-second timeout so a slow or unavailable AI service does not block the user.

**Q6: Why is everything in one HTML file?**

The project has no frontend build tool (no webpack, no Vite, no React). The frontend is
vanilla JavaScript. One file is all that is needed. Express serves it as a static file with
`app.use(express.static(path.join(__dirname, '../../')))`. Splitting it into multiple files
would require a bundler, which would add unnecessary complexity for a project of this scope.

**Q7: How does navigation work without a traditional router?**

It uses SPA hash routing. All pages exist as `<div class="page">` elements in the HTML, all
hidden by default via CSS (`display: none`). The `navigate(page)` function removes the
`active` class from all pages and adds it to the target page. It also updates
`window.location.hash` so the URL reflects the current page. On page load, the code reads the
hash and navigates to the right page, so direct URL access to `/#games` works correctly.

**Q8: How do the two services communicate on Render?**

Through Render's private networking. The `render.yaml` Blueprint defines a `fromService`
reference that gives the Node.js service the internal hostname and port of the Python service.
This hostname is injected as the `AI_SERVICE_URL` environment variable. Requests between the
services stay on Render's private network and do not go through the public internet, which
reduces latency and avoids external network charges.

**Q9: What happens if the AI service is down?**

The screening still works. In `screening.ts`, the AI call is wrapped in a try/catch, and the
`fetch()` uses `AbortSignal.timeout(5000)`. If the request fails or times out, the code logs
"AI service not available, using clinical scoring only" and proceeds with the result from
`scoreMCHATR()`. The fallback SHAP values from `mchat-scorer.ts` use a simplified importance
formula instead of real SHAP values. The user never sees an error; they get a result either way.

### Technology Stack

**Q10: Why TypeScript instead of JavaScript?**

Type safety at the boundary between layers. When I call `prisma.child.findFirst(...)`, TypeScript
knows the return type includes `ageMonths: number` and `userId: string`. When I pass that to
`scoreMCHATR()`, TypeScript confirms the input shape matches the function signature. That
eliminates a whole category of runtime errors — "cannot read property X of undefined" — that
are common in plain JavaScript.

**Q11: What is Prisma and why did you use it over raw SQL?**

Prisma is an ORM that generates a TypeScript client from a schema file. I used it because the
generated client is fully typed — queries return typed objects, not generic `any`. The schema
is readable and version-controlled. Running `prisma db push` applies schema changes without
writing ALTER TABLE statements manually. The tradeoff is less control over the generated SQL
and some performance overhead compared to a query builder like Knex.

**Q12: Explain the Prisma schema. What tables do you have and how are they related?**

Four tables. `User` has email, hashed password, and a one-to-many relation to `Child`. `Child`
stores the child's name, age in months, gender, and has a many-to-one relation to User and
one-to-many relations to both `Screening` and `GameSession`. `Screening` stores the JSON-serialized
answers, the M-CHAT-R score, risk level, optional AI probability, and optional SHAP data.
`GameSession` stores the game type, accuracy, average response time, round count, and the
JSON-serialized round-by-round data.

**Q13: What is SHAP and why does it matter in this application?**

SHAP stands for SHapley Additive exPlanations. It assigns each input feature a contribution
value for a specific prediction — how much did this feature push the model toward a higher or
lower risk score. In a health context this matters because telling a parent "high risk" without
explaining why is not useful. SHAP values let me show: "Eye contact and response to name were
the biggest contributing factors." The `LinearExplainer` from the SHAP library computes these
for logistic regression models efficiently.

**Q14: Why did you train on synthetic data?**

I do not have access to real patient data. Obtaining real M-CHAT-R data requires IRB approval
and data sharing agreements that are not feasible for a portfolio project. The synthetic data
is generated by `train_model.py` using the same clinical scoring rules implemented in
`mchat-scorer.ts`. The model essentially learns to replicate those rules with added noise. I am
transparent about this — the model is a demonstration of how you would wire up a real XAI
pipeline, not a production clinical predictor.

**Q15: Explain the difference between bcrypt and JWT and how you use both.**

bcrypt is for password storage. When a user registers, `bcrypt.hash(password, 10)` produces a
one-way hash that is stored in the database. When they log in, `bcrypt.compare(input, hash)`
verifies the match without ever decrypting the hash. JWT is for session management. After
successful authentication, `jwt.sign({ id, email }, JWT_SECRET, { expiresIn: '7d' })` creates
a signed token the browser stores in localStorage. Every subsequent API request includes this
token in the `Authorization: Bearer` header. The backend verifies it with `jwt.verify()` —
no database lookup needed.

### Security

**Q16: What are the security weaknesses in this project?**

Honestly, several. First, `localStorage` is vulnerable to XSS attacks — if any script injection
occurred, the JWT could be stolen. A `httpOnly` cookie would be safer. Second, the JWTs have
a 7-day expiry with no refresh token mechanism and no server-side revocation, so a stolen token
is valid for its full lifetime. Third, there is no rate limiting on the auth endpoints — a
brute-force attack on login is possible. Fourth, the `JWT_SECRET` in `.env` is a static string;
it should be rotated if compromised. Fifth, `prisma.user.findUnique({ where: { email } })` in
the login route reveals whether an email exists (via the distinct error messages "No account
found" vs. "Incorrect password") — this is an account enumeration vulnerability.

**Q17: How do you protect API routes from unauthorized access?**

The `authMiddleware` function in `backend/src/middleware/auth.ts` is applied to every route
that should be protected. It reads the `Authorization` header, verifies the JWT signature
using `jwt.verify()`, and attaches `{ id, email }` to `req.user`. If the token is missing or
invalid, it returns a 401 response immediately. Routes that use `authMiddleware` also verify
that the resource being accessed belongs to the authenticated user — for example, in
`screening.ts`, the child lookup uses both `id` and `userId: req.user!.id` to prevent a user
from accessing another user's child's data.

**Q18: Why is CORS enabled and what does it do?**

CORS (Cross-Origin Resource Sharing) controls which domains can make requests to the API.
In `index.ts`, `app.use(cors())` enables CORS for all origins. This is intentional because the
frontend and backend are served from the same origin in both development and production — the
`cors()` call here allows the development setup (where you might open the HTML file from a
different port or as a local file) to work. In a stricter production setup, you would
whitelist only specific origins.

**Q19: What does your auth middleware do if the JWT is expired?**

`jwt.verify()` throws a `TokenExpiredError` if the token is past its `expiresIn` date. The
try/catch block in `authMiddleware` catches this (along with `JsonWebTokenError` for invalid
tokens) and returns `401: Invalid or expired token. Please log in again.` The frontend does not
currently handle this response with an automatic redirect — it would show the error message
from the API call.

### Database

**Q20: What are the tradeoffs of storing JSON as strings in SQLite?**

The advantage is simplicity — SQLite does not have a JSON column type, and this approach
works without any schema changes. The disadvantage is that you cannot query inside the JSON
at the database level. For example, you cannot do `WHERE answers->>'q5' = 'true'` to find
all screenings where question 5 was answered yes. Every JSON read requires `JSON.parse()` in
application code, which can throw if the stored data is malformed. The codebase handles this
with explicit `JSON.parse()` calls in child.ts, progress.ts, dashboard.ts, and elsewhere.

**Q21: Why do you use UUIDs instead of auto-incrementing IDs?**

Two reasons. First, UUIDs are not guessable — you cannot enumerate resources by incrementing
an integer ID in the URL (e.g., `/api/report/1`, `/api/report/2`). Second, they can be
generated client-side or in application code without a database round-trip. The schema sets
this with `@default(uuid())`.

**Q22: How does Prisma's `include` feature work?**

`include` is Prisma's syntax for eager loading related records. In `auth.ts`, the login query
uses:
```typescript
prisma.user.findUnique({
  where: { email },
  include: {
    children: {
      include: {
        screenings: { orderBy: { createdAt: 'desc' }, take: 1 },
        gameSessions: { orderBy: { playedAt: 'desc' }, take: 5 },
      }
    }
  }
})
```
This fetches the user, their children, and for each child, the most recent screening and last
5 game sessions — all in a single query. Without `include`, you would need multiple queries.

**Q23: What would you change about the database design for production?**

Several things. Switch from SQLite to PostgreSQL for concurrent write support and persistent
storage. Use Prisma Migrate instead of `db push` to track schema changes as versioned migration
files. Store SHAP data and answer arrays as proper JSON columns (PostgreSQL supports `jsonb`).
Add database-level constraints and indexes — for example, an index on `Screening.childId` and
`GameSession.childId` for faster lookups. Consider separating sensitive health data with
additional access controls.

### Deployment

**Q24: How does the deployment work?**

The project uses Render's Blueprint feature. The `render.yaml` file defines two web services:
`spectrumcare-ai` (Python) and `spectrumcare` (Node.js). When you connect the repository to
Render and apply the Blueprint, Render provisions both services automatically. The Node.js
service runs `npx prisma db push && npm start` on startup to apply schema changes and start
the server. The Python service runs `python app.py`. The AI service's internal URL is
injected into the Node.js service's environment via `fromService.property: hostport`.

**Q25: What is the problem with SQLite on Render's free tier?**

Render's free tier uses ephemeral storage — the file system is reset on every deploy and every
time the service restarts after the 15-minute idle timeout. Since the SQLite database is a
file on the service's disk, all data is lost when the service restarts. This is documented in
`deployment_guide.md` under "Important Notes." For production, you would use a database that
lives outside the application server — a managed PostgreSQL instance that persists regardless
of what the app server does.

**Q26: What are cold starts and why do they happen?**

On Render's free tier, a service that receives no traffic for 15 minutes is "spun down" — the
container is stopped. The next incoming request wakes it up, but the startup process (loading
Node.js modules, connecting to the database, loading the Python ML model) takes 30-60 seconds.
During this time the user sees a loading screen. This is a limitation of free-tier hosting.
Paid tiers keep services running continuously.

**Q27: What environment variables does this project use?**

Four:
- `DATABASE_URL`: The path to the SQLite file. Locally: `file:./dev.db`. On Render: `file:./dev.db`.
- `JWT_SECRET`: The secret key for signing JWTs. Should be a long random string in production.
- `PORT`: The port Express listens on. Defaults to 3001 locally; Render injects this automatically.
- `AI_SERVICE_URL`: The URL of the Python AI service. Locally: `http://localhost:5001`. On Render: injected via private networking.

### Debugging

**Q28: Tell me about a bug you fixed related to the AI service URL.**

When deploying to Render, the Python AI service's internal URL is provided as `host:port`
without the `http://` prefix (for example, `spectrumcare-ai:10000`). Node.js's native
`fetch()` requires a fully qualified URL and throws an error if the protocol is missing. In
development, the URL was always `http://localhost:5001`, so this bug only appeared in the
production environment. The fix was to add a guard in `screening.ts` that checks whether the
URL starts with `http://` or `https://` and prepends `http://` if not. This is the kind of
bug that does not show up locally and only surfaces when you deploy — the reason environment
parity between development and production matters.

**Q29: How do you handle errors in the screening endpoint if the AI service is unavailable?**

The `fetch()` call to the AI service is in its own `try/catch` block inside the outer route
handler. The fetch has a 5-second timeout via `AbortSignal.timeout(5000)`. If the AI call
throws for any reason (timeout, network error, non-OK response), the catch block logs a
message and execution continues with the clinical scoring result. The outer `try/catch`
handles database errors separately. This nested error handling means the user always gets
a response, even in a degraded state.

**Q30: How would you debug a "Child not found" error from the screening endpoint?**

First, I would check that the JWT in the request is valid and the `req.user.id` it contains
matches the user who owns the child. The `child` lookup uses
`prisma.child.findFirst({ where: { id: childId, userId: req.user!.id } })` — if the childId
is valid but belongs to a different user, this returns null and the endpoint returns 404.
Second, I would check whether the child was actually created — open Prisma Studio at
`localhost:5555` and check the Child table. Third, I would log the `childId` and `userId`
values to the console to confirm they match what is in the database.

### Behavioral

**Q31: How did you decide what features to build first?**

I started with the authentication system and database schema because everything else depends
on having users and children in the database. Then the screening flow, because that is the
core value proposition. Then the games, because they needed a child to be associated with.
Then the progress dashboard and PDF report, because those consume data from the features built
earlier. The AI service was built in parallel because it is independent and optional — the
screening works without it.

**Q32: What was the hardest part of this project?**

The hardest part was the AI integration with graceful degradation. Getting the Python service
and Node.js service to communicate in development was straightforward. Making that
communication resilient — handling the case where the URL lacks a protocol prefix, adding a
timeout so a slow AI service does not freeze the screening flow, and ensuring the fallback
clinical scoring produces sensibly formatted output that the frontend can handle — required
thinking through failure modes carefully rather than just the happy path.

**Q33: What would you do differently if you started over?**

I would use PostgreSQL from the start instead of SQLite. The ephemeral storage problem on
Render's free tier is a significant limitation for anyone trying to demo the app, and
switching databases later requires migrating data. I would also use a proper singleton pattern
for the Prisma client — having five separate instances (one per route file) works for SQLite
but would be a problem with connection pooling in PostgreSQL. I would also add rate limiting
to the auth endpoints from day one.

**Q34: How do you approach testing?**

This project does not have automated tests, which is a gap I would address in a production
version. For manual testing, I verified each API route using the browser console and Prisma
Studio to inspect database state. For the AI service, I used the `/health` endpoint to confirm
it is running and tested the `/predict` endpoint directly with curl during development. If I
were adding tests, I would start with integration tests for the auth and screening routes
using a library like Supertest, and unit tests for `mchat-scorer.ts` since it contains pure
scoring logic with no side effects.

**Q35: Tell me about a decision you made that you are not fully happy with.**

Storing the game's SHAP-like values and answers as JSON strings in the database. Because SQLite
does not support JSON columns, I used `JSON.stringify()` before saving and `JSON.parse()` after
reading. This works, but it means every single read requires JSON parsing, you cannot query
inside those fields at the database level, and a malformed stored value would cause a runtime
error. The correct solution for production would be a database that supports native JSON
columns (PostgreSQL with `jsonb`) and proper column types for each field.

### Tricky / Honest Questions

**Q36: What is the weakest part of this project technically?**

The database layer. SQLite with ephemeral storage on Render means data is not persistent in
the deployed environment. The JSON-as-string pattern for complex fields makes the schema harder
to query and more fragile. Multiple Prisma client instances (one per route file) instead of a
singleton is technically incorrect. These are all things I would fix before putting this in
front of real users.

**Q37: Is this app production-ready for real clinical use?**

No, and I am clear about that. Three main reasons. First, the AI model is trained on synthetic
data generated from the same rules it is trying to learn — it is not a validated clinical
predictor. Second, the database is ephemeral in the current deployment, so data is not reliably
persistent. Third, there is no clinician-facing interface, no HIPAA compliance audit, no
data encryption at rest, and no formal security review. The app is a demonstration of how to
build an XAI pipeline in a health context, not a medical device. The disclaimer in the PDF
report makes this explicit.

**Q38: How would you scale this if it needed to handle 10,000 concurrent users?**

First, replace SQLite with a managed PostgreSQL instance (Supabase, Neon, or AWS RDS) with
connection pooling via PgBouncer. Second, add a singleton Prisma client with proper pool
configuration. Third, move to a container-based deployment (Fly.io, AWS ECS, or Kubernetes)
with multiple replicas and a load balancer. Fourth, add a CDN in front of the static
`index.html` so asset serving does not hit the Node.js server. Fifth, add rate limiting
(express-rate-limit) on the auth and screening endpoints. Sixth, add caching for the progress
and dashboard endpoints since those do complex aggregation queries.

**Q39: Why should we trust the M-CHAT-R scoring in your app?**

The scoring logic in `mchat-scorer.ts` is a direct implementation of the published M-CHAT-R
algorithm: 20 questions, a specific at-risk mapping for each question (some where "yes" is
at-risk, some where "no" is), and the clinically defined thresholds (0-2 = LOW, 3-7 = MEDIUM,
8+ = HIGH). The same mapping is duplicated in `train_model.py` for consistency. I would note
that any software implementation should be validated against the published scoring tool before
clinical use, and this app explicitly says it is not a clinical diagnosis.

**Q40: What is the most important thing you learned building this project?**

Building resilient integrations. The AI service call in `screening.ts` taught me to think
about what happens when a dependency is slow, unavailable, or returns unexpected data — not
just when everything works. Adding the 5-second timeout, the try/catch fallback, and the URL
normalization guard were not features I planned upfront; they were responses to things
breaking during development and deployment. The principle is: anything external to your
service will eventually be unavailable or misbehave, and you should design for that from
the start.

## 4. Behavioral Q&A

**Q: Why did you build this project?**

I wanted to build something that connects real technical concepts — machine learning
explainability, REST APIs, database design — to a domain with genuine social impact. Autism
early detection is an area where access to information matters; not everyone has easy access
to a specialist for a preliminary screening. The M-CHAT-R is a validated tool, and building a
digital version of it gave me a concrete problem to solve rather than building another to-do
app.

**Q: How do you learn new technologies?**

My approach is to build something with it immediately rather than working through documentation
linearly. For Prisma, I defined my schema, ran `db push`, and started writing queries against
a real database within an hour. I read documentation when something breaks or when I hit a
limitation I cannot work around by intuition. I also pay attention to the "why" in documentation
— not just what a function does but why it was designed that way, which helps me make better
decisions.

**Q: How do you handle getting stuck on a problem?**

I give myself a time limit for trying to solve it independently — usually 30-45 minutes. If I
am not making progress, I step away and come back with fresh eyes, or I articulate the problem
in writing (like a rubber duck debugging exercise). For the AI service URL bug, I was not stuck
on diagnosing it; I had the error message. But the bug only appeared in production, which meant
I had to reason about what was different between the local and production environments without
being able to attach a debugger.

**Q: How do you handle feedback that your code needs significant changes?**

I try to understand the reasoning before asking questions about the specific change. If a code
reviewer says "this should be a singleton," my first question is why — what problem does the
current pattern cause? Once I understand the underlying concern, I can either implement the
suggested change or propose an alternative that addresses the same concern differently. I have
found that pushing back on feedback without first understanding it is almost always wrong.

**Q: What is a weakness you are actively working on?**

Testing. This project has no automated tests, and that is a gap I am aware of. I know how to
write tests conceptually, but in practice I prioritize building features first and testing
feels like it slows me down. The counterargument — that tests would have caught the Prisma
singleton issue and the JSON parsing fragility before they became bugs — is persuasive, and I
am trying to build the habit of writing at least unit tests for pure functions as I go.

**Q: Describe a time you had to learn something quickly under pressure.**

During this project, I needed to understand SHAP values well enough to integrate them
meaningfully into the UI — not just display raw numbers, but show them as labeled bars with a
"risk" or "protective" direction. I read the SHAP documentation, looked at examples of the
`LinearExplainer`, and traced through how the values would look for a logistic regression
model with three output classes. That took a few hours of focused reading and experimentation.
The key was knowing what question I was trying to answer: "given a prediction, how do I tell
the user which specific questions drove the result?"
